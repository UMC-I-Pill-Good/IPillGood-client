## 📌 프로젝트 소개

나에게 맞는 영양제 추천부터 루틴 형성까지, 개인 맞춤 영양제 추천 웹앱 서비스 **아필굿(I Pill Good)**!

> 💊 Pill Good? Feel Good!

웰니스 트렌드 속에서 영양제에 관심을 갖는 사람들은 늘고 있지만, 수백 가지 제품과 넘쳐나는 정보 앞에서 정작 '나에게 맞는 영양제'를 찾지 못하는 경우가 많습니다.

아필굿은 나이·성별·직업·건강 고민 등 개인 건강 정보를 기반으로 AI가 맞춤 영양제를 추천하고, 컨디션에 따라 오늘 필요한 영양제까지 제안하는 웹앱 서비스입니다. 식약처 데이터를 활용한 성분 투명도 리포트로 광고가 아닌 근거 있는 정보를 제공하며, 일일 섭취 체크·캘린더·캐릭터 성장 요소를 통해 꾸준히 먹는 습관까지 함께 만들어갑니다.

| 목표                     | 내용                                                                 |
| ------------------------ | -------------------------------------------------------------------- |
| 💊 맞춤 추천 & 루틴 형성 | 개인 건강 정보 기반 AI 추천 + 일일 섭취 체크로 꾸준한 복용 습관 형성 |
| 💡 신뢰할 수 있는 정보   | 식약처 데이터 기반 성분 투명도 리포트 제공                           |
| 🔎 탐색 & 비교           | 필터링 기반 랭킹·검색, 성분·함량 직접 비교                           |
| 🗄️ 영양제 통합 관리      | 보유 영양제 관리 + 병용 금기 안내                                    |
| 🧪 컨디션 기반 추천      | 주간 컨디션 기록 기반 영양제 & 대체 음식 추천                        |

## 📁 폴더 구조

**설계 원칙**

- Next.js App Router + Feature 기반 아키텍처
- `app` 라우팅/전역 설정 · `features` 비즈니스 기능 · `shared` 공통 모듈로 역할 분리
- 다른 도메인과의 의존성 최소화

**네이밍 규칙**

- 컴포넌트/파일명: PascalCase (ex. `UserAuth.tsx`)
- 폴더명: 소문자 (ex. `home`, `cabinet`, `login`)

```
src/
├── assets/                               # 이미지, 아이콘, 폰트 등 정적 리소스
│
├── app/
│      ├── _providers/                    # 전역 Provider 관리
│      ├── (public)/                      # 누구나 접근 가능
│      ├── (protected)/                   # 로그인된 사용자만 접근 가능
│      ├── admin/                         # 관리자 계정만 접근 가능
│      ├── api/                           # API 공통 인스턴스 정의
│      ├── layout.tsx                     # 최상위 루트 레이아웃
│      ├── error.tsx
│      ├── not-found.tsx
│      └── globals.css
│
├── features/                             # 도메인(비즈니스 기능) 단위 관리
│       ├── home/
│       │       ├── api/
│       │       ├── hooks/
│       │       ├── components/
│       │       └── types/
│       ├── cabinet/
│       ├── login/
│       └── ...
│
└── shared/                               # 공통 모듈
        ├── components/                   # Button, Modal, Input 등
        ├── layout/                       # 전역 레이아웃 요소 (Header, NavBar 등)
        ├── hooks/
        ├── utils/
        ├── constants/
        └── types/
```

## 🌿 브랜치, 커밋, 이슈, PR 컨벤션

### 1️⃣ Branch

`main → develop → feature` 흐름을 따른다.

| 브랜치                     | 용도                                        |
| -------------------------- | ------------------------------------------- |
| `main`                     | 배포용. 직접 push 금지, PR로만 병합         |
| `develop`                  | 개발 통합 브랜치. 모든 기능 브랜치의 분기점 |
| `feature/#이슈번호-기능명` | 새로운 기능 개발. ex) `feature/#1-login-ui` |
| `fix/#이슈번호-버그명`     | 버그 수정. ex) `fix/#2-login-null-error`    |
| `hotfix/#이슈명`           | main 브랜치 긴급 버그 수정                  |
| `refactor/#명칭`           | 기능 변경 없는 코드 개선                    |

**브랜치 규칙**

1. 기능 개발은 반드시 **feature** 브랜치에서 개발 — 브랜치명은 _**kebab-case**_ 사용
2. 개발 완료 시 **develop** 브랜치로 병합
3. 모든 QA 및 버그 수정 완료 시 **develop**으로 병합
4. 긴급 수정은 **hotfix** 브랜치에서 진행 후, **main**으로 병합

---

### 2️⃣ Commit

```
[#이슈번호] <타입> : <메세지>

# 예시
[#12] feat : 로그인 API 연동
[#24] feat : 북마크 알림 설정 기능 추가
```

| 타입       | 설명                              |
| ---------- | --------------------------------- |
| `feat`     | 새로운 기능 추가                  |
| `fix`      | 버그 수정                         |
| `docs`     | 문서 수정                         |
| `refactor` | 코드 리팩토링                     |
| `style`    | 포맷, 공백 등 스타일 변경         |
| `chore`    | 파일 이동/이름 변경, 주석 추가 등 |
| `build`    | 라이브러리 설치                   |

- 커밋 메세지는 **한글**로 작성
- 커밋 타입은 **영문 소문자**로 작성

---

### 3️⃣ Issue

**이슈 이름 형식:** `[FEAT | BUG | REFACTOR] 이슈 내용`

| 유형      | 제목 형식             |
| --------- | --------------------- |
| 기능 개발 | `[FEAT] 기능 내용`    |
| 버그      | `[BUG] 버그 내용`     |
| 리팩토링  | `[REFACTOR] 리팩토링` |

---

### 4️⃣ PR 템플릿

```markdown
## 📂 관련 이슈

- closes #[이슈 번호]

## 📝 작업 내용

- 작업 내용 1
- 작업 내용 2

## 📸 스크린샷

## ✅ 변경 사항 체크리스트

- [ ] 기능 동작 확인
- [ ] 타입 에러 없음
- [ ] 기존 기능에 영향 없음
- [ ] 테스트 코드 추가 또는 기존 테스트 통과

## 🔧 추가 사항

> 아직 완료 못한 작업, 리뷰어가 알면 좋은 내용, 향후 개선 아이디어 등
```

**머지 조건**

- `main`, `develop`에 직접 push 금지 — 반드시 PR로만 병합
- PR은 팀원 **1명 이상의 approve** 필요
- GitHub Actions CI 통과 필수
